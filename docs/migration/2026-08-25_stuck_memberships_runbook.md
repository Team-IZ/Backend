# 데이터 정리 요청 — 해체된 팀에 팀원 17명이 배정된 채 갇혀 있습니다

> 2026-08-25 · 요청 박종호(백엔드) → **DB 운영 담당**
> 대상 **`team_membership` 17행의 `to_at`만 채움** · 삭제 없음 · 스키마 변경 없음
> 근거: 47차 대응 중 실 DB 확인. 47차 R1·R2 자체는 **이미 해소됐습니다**(아래 참고)

**요청 사항** — 아래 2단계를 이 순서로 실행해 주세요. 0단계 결과가 기대값과 다르면
멈추고 알려 주시면 됩니다.

## 1. 무엇을 하나

`team.deleted_at`이 찍혔는데 `team_membership.to_at`이 비어 있는 행의 `to_at`에
**이 트랜잭션의 시각**을 넣습니다. 그것뿐입니다.

| | |
|---|---|
| 대상 | J반 미프 5차 유령 4팀(`1팀`·`2팀`·`4팀`·`6팀`)의 소속 **17행** |
| 바뀌는 것 | `to_at` NULL → 트랜잭션 시각 |
| 안 바뀌는 것 | `team` 행, 소속 행 자체, 살아 있는 팀의 소속(수로 대조합니다) |

### 왜

팀 해체는 `team.deleted_at`을 찍는 것과 그 팀 소속에 `to_at`을 찍는 것을 **함께** 해야
합니다. 46차 수정 **이전**의 해체는 앞의 하나만 했습니다. 그래서 08-24에 해체된 J반
1·2·4·6팀에 17명이 배정된 채 남아 있습니다. 같은 반 `3팀`은 08-25 08:41 해체 — 46차 수정
이후라 정상적으로 풀렸습니다. **그 대조가 원인을 특정해 줍니다.**

조회는 `JOIN team … deleted_at IS NULL`로 유령 팀을 걸러 내므로 화면에는 이미 미배정으로
보입니다. 문제는 재배정할 때입니다 — 새 소속 행이 생겨도 갇힌 행이 남아 한 사람이
**활성 소속 2건**을 갖게 됩니다. 정의서가 "프로젝트당 활성 TeamMembership 최대 1건"이라고
못 박은 자리인데 DB 제약이 없어 조용히 어긋납니다. 아직 아무도 재배정되지 않았습니다.

### 왜 `deleted_at`이 아니라 트랜잭션 시각인가

17행 **전부** `from_at`이 팀의 `deleted_at`보다 **뒤**입니다.

| 팀 | 해체(`deleted_at`) | 최초 배정(`from_at`) |
|---|---|---|
| J반 1팀 | 08-24 15:23:08 | 08-24 **16:57:43** |
| J반 2팀 | 08-24 15:22:39 | 08-24 **16:57:49** |
| J반 4팀 | 08-24 15:22:42 | 08-24 **16:58:03** |
| J반 6팀 | 08-24 09:41:34 | 08-24 **16:58:16** |

**팀이 해체된 뒤에 사람이 배정됐습니다.** 46차 이전에는 조회에 `deleted_at` 필터가 없어
해체된 팀이 배정 대상 목록에 그대로 남았고, 거기에 배정이 실제로 들어갔습니다. 46차
`TeamRepository` 수정이 막은 것이 바로 이 경로입니다.

그래서 `to_at`에 `deleted_at`을 넣으면 `from_at > to_at`이 되어
`ck_team_membership_period_order`를 깹니다. 의미로도 거짓입니다. 트랜잭션 시각을 넣으면
사실대로 남습니다 — 그 사람은 08-24 16:57부터 **이 정리 시점까지** 해체된 팀에 배정된
상태였다. 한 트랜잭션 안의 모든 행이 같은 값을 받으므로 그 값 하나로 되돌릴 수도 있습니다.

## 3. 실행

### 0단계 — 사전 확인

```bash
psql "$PGURL" -f docs/migration/2026-08-25_precheck_stuck_memberships.sql
```

| 항목 | 기대값 | 다르면 |
|---|---|---|
| 1. 갇힌 소속 | J반 1·2·4·6팀 네 줄 | 다른 반이 나오면 알려 주세요 — 범위가 넓어집니다 |
| 2. 합계 | **17행 / 4팀** | 크게 다르면 그 사이 편성이 바뀐 것이니 **알려 주세요** |
| 3. 해체 후 배정 | 17행 전부 해당 | 판단 불필요. 값 선택 근거를 보여 줄 뿐입니다 |
| 4. 이중 소속 | **0줄** | 줄이 나오면 이미 재배정된 사람이 있다는 뜻 — 백필이 그것도 정리합니다 |
| 5. 살아 있는 팀의 활성 소속 | 그 수를 적어 두세요 | 백필 후 같아야 합니다 |

### 1단계 — 적용

```bash
psql "$PGURL" -f docs/migration/2026-08-25_backfill_stuck_memberships.sql
```

기대 출력: `NOTICE 참고 — 17행은 … 해체된 뒤에 배정된 행입니다` → `NOTICE 통과 — 대상 17행`
→ `UPDATE 17` → `STEP 4-1` 0줄 → `STEP 4-2` before = after →
**`STEP 4-3`이 출력하는 `applied_to_at` 값을 기록해 두세요**(되돌릴 때 씁니다) →
`STEP 4-4` 풀려난 17명 / 다른 팀 소속 0 → `NOTICE 통과` → `COMMIT`.

이미 정리된 DB에서 다시 돌려도 `대상 없음` NOTICE만 찍고 아무것도 바꾸지 않습니다.

## 5. 되돌리기

지운 것이 없어 되돌릴 수 있습니다. 본 작업 파일 맨 아래 롤백 SQL에 `STEP 4-3`이 출력한
값을 넣으면 그 17행만 정확히 원복됩니다 — 다른 경로가 남긴 `to_at`은 마이크로초 단위로
달라 걸리지 않습니다.

## 6. 참고 — 47차 R1·R2는 이미 해소됐습니다

이 요청은 47차의 후속이지만 47차 증상 자체와는 별개입니다. 부분 UNIQUE 마이그레이션
(`docs/migration/2026-08-25_team_unique_active_scope.sql`)이 **UTC 08:41~08:49 사이에 이미
적용**됐습니다 — 같은 반에 이름 `7팀`인 행이 둘, E반에 번호 `1`인 행이 둘 공존하는 것이
그 증거입니다(전체 UNIQUE 아래에서는 불가능).

```
08:25:22  G반 7팀 해체              ← 47차 R1의 DELETE
08:26:54  G반 "7팀" 생성 → 409       ← 47차 R1
08:41:34  J반 3팀 해체
   ‥‥‥‥  부분 UNIQUE 마이그레이션 적용
08:49:15~19  E반 1~5팀 생성 성공      ← R2 해소
08:49:52     G반 7팀 재생성 성공      ← R1 해소
```

유령 행을 하드 삭제하려던 `2026-08-25_purge_ghost_teams.sql` 세트는 **철회**했습니다.
이름·번호 압박이 사라져 지울 이유가 없어졌기 때문입니다. 그 파일들은 저장소에 넣지 않고
`docs/data-fix/`(gitignore 대상)에 배너만 달아 기록으로 남겼습니다.

## 7. 검증 기록

임시 PostgreSQL 16 컨테이너에 `PostgreSQL_DDL_v08.sql`을 적재(73 테이블, 에러 0건)하고
**현재 운영과 같게 부분 UNIQUE 인덱스를 유지**한 채, 실 DB 덤프의 `class` · `project` ·
`team` · `team_membership` 전량(1,923팀 / 6,780행)을 넣고 실측했습니다.

- 사전 확인: 갇힌 소속 17행 / 4팀, 해체 후 배정 17행, 이중 소속 0, 살아 있는 활성 소속 6,749
- 본 작업: `UPDATE 17` → 해체된 팀의 활성 소속 0, 살아 있는 활성 소속 6,749 **불변**,
  풀려난 17명 전원이 어느 팀에도 활성 소속 없음
- 되돌리기: `STEP 4-3` 값으로 `UPDATE 17` → 갇힌 소속 17행으로 정확히 원복
- 가드: `from_at`을 미래로 심으니 `🔴 중단 — from_at이 현재 시각보다 뒤인 행이 1건`으로
  멈추고 17행 그대로 유지
- 재실행: 정리된 DB에서 `대상 없음` NOTICE만, 무변경
