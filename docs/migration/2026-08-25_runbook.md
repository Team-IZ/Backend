## 1. 무엇을 고치나

AI 분석은 `SUCCEEDED`로 끝났는데 결과가 DB에 적재되지 않는 경로가 있습니다. 그때 백엔드가
응시를 대신 닫으면서 이 흔적이 남습니다.

```
analysis_job.status = 'SUCCEEDED'  AND  analysis_job.analysis_id IS NULL
measurement_attempt.status = 'FAILED'  AND  terminal_reason_code = 'ANALYSIS_FAILED'
```

이 뷰의 판정식 넷이 분석 실패를 `analysis_job.status`로만 읽어서 위 조합을 못 봅니다.
결과가 아래입니다.

| 컬럼 | 지금 | 적용 후 |
|---|---|---|
| `representative_status` | `ANALYZING` (분석 중) | `ANALYSIS_FAILED` (분석 실패) |
| `default_action_code` | `NONE` → **버튼이 안 그려짐** | 마감 전 `RESUBMIT_ZIP`/`RESUBMIT_REPOSITORY`, 마감 후 `CONTACT_MANAGER` |
| `analysis_phase` | `COMPLETED` (거짓) | `FAILED` |
| `analysis_failure_code` | `null` | `ANALYSIS_FAILED` |
| `warning_codes` | `{}` | `{ANALYSIS_FAILED}` |

학생 화면은 「코드 분석이 진행 중이에요」 + 버튼 없음 카드를 봅니다. **재제출하면 복구되는
상황인데 재제출 버튼이 없습니다.** 이걸 되살리는 것이 이 작업의 실질적 성과입니다.

같은 회차의 리포트 화면은 응시 원장을 직접 읽어 이미 「분석 실패」라고 말하고 있었습니다.
두 화면이 같은 학생을 두고 다른 말을 하던 것을 맞추는 작업이기도 합니다.

## 3. 이미 끝낸 검증

임시 Postgres 16 컨테이너에 정본 DDL·View를 올려서 확인했습니다.

- 정본 로드 **에러 0** (73 테이블 / 52 뷰, `citext`·`btree_gist` 확장 필요)
- 마이그레이션 적용 성공, **69컬럼 시그니처 완전 동일** → `CREATE OR REPLACE` 확정
- 정본 파일 수정본과 마이그레이션 적용본의 `pg_get_viewdef` **바이트 단위 일치**

- 판정식을 **14개 시나리오로 적용 전후 대조**

| 시나리오 | 적용 전 | 적용 후 |
|---|---|---|
| 결과 없는 성공 · 마감 전 | `ANALYZING` / `NONE` | `ANALYSIS_FAILED` / `RESUBMIT_REPOSITORY` |
| 〃 마감 후 | `ANALYZING` / `NONE` | `ANALYSIS_FAILED` / `CONTACT_MANAGER` |

## 4. 제안서와 한 곳 다릅니다 — 재분석 중 가드

제안서는 `terminal_reason_code = 'ANALYSIS_FAILED'`만 보라고 썼는데, 그러면 **학생이 재제출한
직후**가 문제가 됩니다. 백엔드가 `FAILED` 응시를 건드리지 않기 때문에 종료 사유는 남아 있는데
`analysis_status`는 새 job의 `QUEUED`/`RUNNING`이 됩니다. 방금 재제출한 학생에게
「분석 실패 + 재제출」 카드를 다시 보여주면 중복 제출을 유도합니다.

그래서 새로 넣는 판정마다 아래를 함께 걸었습니다. 재분석이 도는 동안에는 종전대로
`ANALYZING` / `WAIT_FOR_ANALYSIS`입니다.

```sql
AND a.analysis_status::text IS DISTINCT FROM 'QUEUED'::text
AND a.analysis_status::text IS DISTINCT FROM 'RUNNING'::text
```

`= ANY` 대신 `IS DISTINCT FROM` 두 줄인 것은, `analysis_status`가 NULL일 때 `<> ALL`이
`true`가 아니라 NULL이 되어 절이 통째로 죽기 때문입니다.

## 5. 이 작업이 하지 않는 것

- **프론트엔드 배포 불필요.** `ANALYSIS_FAILED`는 새로 만드는 값이 아니라 기존 계약값입니다
  (`TraineeRepresentativeStatus`). 라벨·배지·버튼 경로가 이미 전부 준비돼 있습니다.
- **백엔드 배포 불필요.** 판정이 전부 뷰 안에 있습니다.
- **이미 닫힌 응시를 되살리지 않습니다.** `code_analysis`가 없으면 문항도 세션도 없습니다.
  학생이 **재제출**해야 복구되고, 그 경로는 이미 있습니다
  (`JdbcAssessmentSessionPreparer.markAttemptsReady`). 이 작업의 성과는 학생이 상황을 정확히
  보고 **재제출로 행동할 수 있게** 되는 데까지입니다.
- **`measurement_attempt`를 직접 UPDATE하지 마세요.** 손으로 `SESSION_READY`로 바꾸면
  문항 없는 빈 세션이 열립니다.

### 근본 원인은 이미 해결됐습니다

8/24 미프 4차 15건은 AI가 정상 범위로 만드는 `FAIL` + `evidence` 없음 조합을
`ck_project_requirement_assessment_result_fields`가 거부해 적재 트랜잭션이 통째로 롤백된
것이었고, 그 CHECK는 `2026-08-25_requirement_assessment_fail_allows_no_evidence.sql`로
완화해 이미 머지했습니다. 다만 **그때 이미 닫힌 응시는 저절로 되살아나지 않습니다.**
